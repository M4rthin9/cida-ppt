# Setup and operations

## Local development

The Next.js 16.4.0 / React 19.3.0 application needs Node 22+, pnpm 10.33.0 and PostgreSQL 16. Development and production builds use Turbopack by default. Keep a persistent PostgreSQL volume and a writable media directory; the CMS is not backed by browser storage or JSON fixtures.

For a complete local Docker stack:

```bash
docker compose -f docker-compose.dev.yml up --build
```

The development image installs locked dependencies; the startup command applies migrations, seeds the four categories, 82 approved products and their media, then starts Next.js at http://localhost:3000. Create an owner inside that container using `ADMIN_PASSWORD` supplied through your shell or secret manager. The seed never creates an administrator.

For host development, start only PostgreSQL:

```bash
docker compose -f docker-compose.dev.yml up -d db
cp .env.example .env
pnpm install --frozen-lockfile
pnpm db:migrate
pnpm db:seed
pnpm dev
```

Use `postgres://cida:cida@localhost:5432/cida` for this local database; the `db` hostname works only inside Docker. Use an absolute, writable `MEDIA_DIR`. Set `AUTH_SECRET` to at least 32 random characters, generated with `openssl rand -base64 32`.

On PowerShell use `pnpm.cmd` if the PowerShell shim is blocked. Supply `ADMIN_PASSWORD` via a secure prompt or your secret manager; do not commit it or put a real password in a command argument.

For a local production build on Windows without symbolic-link permissions, set `$env:NEXT_STANDALONE = 'false'` before `pnpm.cmd build` and keep that value for `pnpm.cmd start`. This builds the normal Next.js server output without the deployment bundle. Leave this variable unset for Linux, Docker and CI, which keep the existing standalone deployment output. No operating-system permission changes are needed for local review.

When a development server is also running, set `$env:NEXT_DIST_DIR = '.next-production'` for both the production build and start commands. This keeps production output separate from the dev server's `.next` folder. The default output directory remains `.next`.

## Production configuration

Set these before building and running:

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | PostgreSQL connection with appropriate TLS/network controls |
| `AUTH_SECRET` | Unique random authentication secret, at least 32 characters |
| `AUTH_URL` | Actual HTTPS origin for authentication and upload origin checks |
| `NEXT_PUBLIC_SITE_URL` | Same public origin; included in metadata/build output |
| `MEDIA_DIR` | Persistent writable filesystem media directory |
| `LINE_OA_URL` | Initial LINE destination; editable later in CMS settings |
| `SMTP_*` | Optional mail delivery; enquiries are always stored first |
| `DATABASE_POOL_MAX` | Optional pool limit, default 10, maximum 20 |
| `DATABASE_MAX_PIPELINE` | Optional driver pipeline limit, default 100 |

The default LINE destination was retained from the existing project. Confirm public contact details in `/admin/settings/contact` and LINE settings before launch. Enable indexing in `/admin/settings/seo` when content is ready; the default is noindex.

The repository includes the existing Docker/Caddy/backup infrastructure, adapted to the `cida-ppt` project. It does **not** provision a server or change DNS. For its Cloudflare Origin Certificate setup, supply `SITE_DOMAIN`, the real `AUTH_URL` and `NEXT_PUBLIC_SITE_URL`, `WEB_IMAGE`, `POSTGRES_PASSWORD`, a Cloudflare Origin Certificate under `certs/`, and the trusted proxy snippet generated by `scripts/cloudflare-ips.sh`. Review the existing provisioning script before running it on a host: it changes firewall and operating-system settings.

Set GitHub repository variable `SITE_URL` to the real HTTPS origin and manually run **Release** to create a GHCR image. The workflow does not deploy. Alternatively build on a suitably sized build machine:

```bash
pnpm db:migrate
pnpm db:seed
pnpm build
docker build -t cida-ppt:review .
```

Do not leave a production `.env` in the build checkout: Next standalone output may copy it. Supply build variables via the environment or your CI secret manager. The runtime image uses a non-root user and a persistent media volume. Never use `docker compose down -v` on production unless destroying all data is intended.

Apply migrations before starting the new application version. For a fresh database run the seed once; re-running is safe and does not overwrite CMS changes. For an existing populated database, take a database/media backup and review the vocational migration and old content before publishing.

`pnpm db:seed` and `pnpm db:seed:production` now install the approved catalogue and public settings from [content/production-seed](content/production-seed/README.md), including all product photographs, homepage category backgrounds, full-width desktop banners and mobile banners. Set `DATABASE_URL` and `MEDIA_DIR` first. To validate without changing the database or media, run `pnpm db:seed --dry-run`. The earlier category-only seed remains available as `pnpm db:seed:configuration`.

Run `pnpm db:seed:verify` to check migrations, fresh installation, image hashes, repeated runs and preservation of CMS edits in an isolated temporary database. The configured database role needs permission to create that test database. After approving newly published products in the CMS, run `pnpm db:seed:export`, verify the refreshed seed, and commit `content/production-seed/` with its image files. Raw catalogue sources, draft reviews and source animation frames remain local; deployable images and optimized public frames stay tracked. `pnpm-lock.yaml` is the canonical lockfile.

The production Docker image includes the seed and its image files. On a configured deployment host, initialise the database and the persistent media volume before starting the website:

```bash
docker compose run --rm --no-deps --entrypoint node web scripts/migrate.mjs
docker compose run --rm --no-deps --entrypoint node web scripts/seed-production.mjs
docker compose up -d web
```

The database service must be healthy before these commands. Seeding is explicit; deployment does not reset catalogue content. Existing names, prices, translations, gallery selections, settings and image files are preserved. Existing categories with missing hero or homepage backgrounds acquire those missing images. A conflicting SKU, slug or media identity stops the seed before database changes. No administrator, password, private enquiry, session or audit history is included.

## Administrator workflow

1. Create the first owner with `pnpm admin:create`, then log in at `/admin`.
2. Review and publish category descriptions and media.
3. Add genuine products with a category, optional SKU, descriptions, price mode and stock information.
4. Upload authentic images; use the arrows to put the cover first. Removing an image from a product does not delete its original from storage.
5. Save a draft, then publish. Featured products are selected by the CMS checkbox.
6. Archive before permanently deleting a product. Only owners may permanently delete, with typed confirmation. Restore returns it to draft.
7. To delete a category containing products, choose a replacement category. Archived products move as well.
8. Add vocational news only. Publication time is shown in the administrator's local timezone.

Owners can choose **LINE Official Account (OA)** or **เพิ่มเพื่อนด้วยเบอร์โทรศัพท์** in `/admin/settings/line`. Enter the OA handle or the LINE-registered phone number for the selected mode. The other value stays available for switching back. OA mode opens the official add-friend/product chat link; phone mode opens a matching page with a copyable number, add-friend steps and a copyable product inquiry. The contact page, footer and product buttons use the selection. The seed retains the current OA selection with an empty phone field; it does not publish an example phone number.

Editors can manage products, categories, media, news and inquiries. Owners also manage users, system settings and permanent product deletion. Disabling accounts or resetting passwords invalidates existing sessions; the server rechecks current database permissions.

## Cinematic assets

The homepage opens with two scroll-driven stages: `CinematicHero` and `ApertureSection`. Optimized posters appear immediately, the first sequence loads automatically, and the second prewarms near the hand-off. The chapter rail includes a shortcut to the collections. Both sequences are optional; missing sets render static compositions. Reduced-motion and JavaScript-free views show readable posters without downloading frame sequences. Check the opening with `node scripts/verify-cinematic-home.mjs` against a local server on port 3001 (or set `DESIGN_QA_URL`).

Import a sequence from a folder of frames or a ZIP, into either named set:

    pnpm frames:import "frames/merged_20s_frames" --set hero --encode
    pnpm frames:import "frames/clip2_frames" --set reveal --encode

The importer reads every PNG or JPEG in natural order, samples the set down to exactly 150 frames (`--max` takes 8 to 600), checks that every frame decodes and shares one size, and writes `manifest.json` last so a rejected import leaves the previous sequence intact. It copies the original bytes by default; `--encode` re-encodes for delivery instead (JPEG quality 76 at up to 1280px, tunable with `--quality` and `--width`), which took the supplied 20-second set from 139 MB to 17.3 MB. A sequence that would serve more than 40 MB is refused rather than published, since one that large never keeps up with the scroll; `--allow-large` overrides that deliberately. Starting from a video instead, run `pnpm frames:make` first. Frame delivery can later move to a CDN while keeping the same manifest contract. See [docs/SCROLL-SEQUENCE.md](docs/SCROLL-SEQUENCE.md).

The production seed uses the supplied real product catalogue and the approved studio photographs. Review stock availability and contact information through the CMS before launch, and add genuine vocational news there. The hero's no-footage fallback is explicitly labeled as a conceptual illustration, and the aperture section falls back to a typographic panel rather than to stock imagery.

## Backups and recovery

Keep PostgreSQL **and** the media volume together in backups. The existing `scripts/backup.sh` and `scripts/restore.sh` provide database/media backup and restore commands; test restoration on a separate environment before relying on them. Store an additional encrypted copy outside the application host. Soft deletion retains original media; deliberate permanent filesystem cleanup is an operator task.

For an account lockout, run `pnpm admin:create` with the existing email and a new strong `ADMIN_PASSWORD`. For deployment rollback, use the previous immutable image tag after confirming schema compatibility; schema rollback may require a tested database restore. `GET /api/health` verifies process availability only.
